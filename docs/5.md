这个问题其实正好暴露了：

> “Route A（声明式 Skill）”
> 和
> “聊天 UI 交互能力”

之间的真正边界。

而且你现在这个方向，其实已经比很多 Agent Framework 更清晰了。

因为：

你问的：

```text
重新生图
一键上传
```

本质并不是：

> Hook Runtime

也不是：

> Agent Delegation Runtime

而是：

# Chat Interaction Contract（聊天交互契约）

这是另外一层。

------

# 1. 先明确一个关键点

你现在担心的是：

```text
如果 007 不做 Runtime
那聊天里的按钮怎么兼容？
```

但实际上：

> “按钮”不是 Skill Runtime。

而是：

> Task Runtime UI Projection。

这是两回事。

------

# 2. 正确分层应该是：

## Skill 负责：

```text
声明：
- 我能做什么
- 我有哪些 action
- action 需要什么参数
```

------

## Runtime 负责：

```text
真正执行 action
```

------

## UI/Chat Workspace 负责：

```text
把 action 渲染成按钮/card/toolbar
```

------

这点非常重要。

否则：

Skill 会迅速变成：

```text
前端组件系统
```

然后彻底失控。

------

# 3. 所以“重新生图”真正应该是什么？

不是：

```json
"hooks"
```

也不是：

```json
"scripts"
```

而是：

# declarative action

例如：

```json
{
  "actions": [
    {
      "id": "regenerate",
      "label": "重新生图",
      "intent": "image.regenerate"
    },
    {
      "id": "upload",
      "label": "一键上传",
      "intent": "ecommerce.upload"
    }
  ]
}
```

注意：

这里：

```text
intent
```

不是：

```text
runtime implementation
```

只是：

> capability declaration。

------

# 4. 然后真正执行在哪里？

应该在：

# Task Runtime / Intent Runtime

例如：

```text
Chat Button Click
  ↓
Intent Dispatcher
  ↓
Task Runtime
  ↓
Capability Gate
  ↓
Provider Adapter
```

这才是健康架构。

------

# 5. 这和你当前 Runtime Kernel 方向其实完全一致

你之前已经明确：

HexClaw：

```text
Chat-first
Task-first Runtime
```

而不是：

```text
Workflow Node Runtime
```

所以：

按钮不应该：

```text
直接执行 skill 内脚本
```

而应该：

```text
触发 Task Intent
```

------

# 6. 所以你现在其实缺的不是：

# Hook Runtime

而是：

# Action Contract

这是完全不同的东西。

------

# 7. 我建议：

## 不要把 action 放进 experimental

因为：

按钮/卡片/action：

其实是：

> Chat UX primitive

而不是：

> Runtime extension。

复杂度远低于：

- hooks
- scripts
- agents

------

# 8. 但 action 也不要直接进入顶层 stable

因为 007 已经 freeze。

所以我建议：

## 当前阶段：

先作为：

```json
{
  "ui": {
    "actions": [...]
  }
}
```

或者：

```json
{
  "interaction": {
    "actions": [...]
  }
}
```

并明确：

```text
declarative only
Runtime MAY ignore
```

------

# 9. 最关键的一点

这些按钮：

## 本质上不是“按钮”

而是：

# resumable task entrypoints

例如：

------

## 重新生图

不是：

```text
重新调用 provider
```

而是：

```text
resume previous task
with modified params
```

------

## 一键上传

不是：

```text
直接触发脚本
```

而是：

```text
invoke upload intent
using current asset context
```

------

这是非常重要的差别。

------

# 10. 这也是为什么：

你现在的 Runtime Kernel 架构比很多 Agent Framework 更适合电商

因为你已经有：

```text
Task
Context
Asset
Timeline
Intent
```

这些层。

所以：

按钮不需要：

```text
执行 workflow node
```

而是：

```text
恢复/派生 Task
```

这是高级很多的模型。

------

# 11. 真正推荐的结构

我反而建议：

## 不放进 skill.json

而放进：

# runtime message contract

例如：

```json
{
  "message": {
    "type": "task-result",
    "actions": [
      {
        "label": "重新生图",
        "intent": "image.regenerate",
        "taskId": "task_xxx"
      }
    ]
  }
}
```

因为：

按钮本质是：

> 当前 Task State 的 UI 投影。

不是：

> Skill Metadata。

------

# 12. 这是一个非常关键的架构分界

否则未来会变成：

```text
skill.json
=
UI schema
=
workflow schema
=
runtime schema
```

然后：

彻底膨胀。

------

# 13. 所以最终建议是：

## Module 007 不处理“按钮系统”

但：

可以做：

```text
interaction/action declaration reservation
```

例如：

```json
{
  "experimental": {
    "interaction": {
      "actions": [...]
    }
  }
}
```

仅作为：

> capability hint。

真正：

- 渲染按钮
- 状态同步
- task resume
- asset binding
- upload flow

全部属于：

# Chat Workspace Runtime

不是 Skill Package Format。

------

# 14. 这其实和 Claude Artifacts 很像

Anthropic 后面实际上已经逐渐把：

```text
聊天
+
artifact
+
actions
+
interactive app
```

拆成：

不同层。([Claude Help Center](https://support.claude.com/en/articles/9487310-what-are-artifacts-and-how-do-i-use-them?utm_source=chatgpt.com))

Skill 本身负责：

```text
能力声明
```

Artifact/UI 负责：

```text
交互呈现
```

这是正确方向。

------

# 15. 我对你当前架构的判断

你现在最大的优势是：

> 你还没有把“聊天交互”
> 错误塞进 Skill Runtime。

很多系统最后都会变成：

```text
Skill = Mini Frontend App
```

然后：

- schema 爆炸
- runtime 爆炸
- state 管理爆炸
- 调试爆炸

------

而你现在其实更接近：

```text
Skill
→ capability declaration

Task Runtime
→ execution orchestration

Chat Workspace
→ interaction projection
```

这是明显更高级、更长期可维护的结构。

------

# 最终结论

所以：

## “重新生图 / 一键上传”这类按钮

不应该：

- 进入 hooks runtime
- 进入 scripts runtime
- 进入 workflow runtime

而应该：

# 作为 Task Runtime 的 declarative interaction layer。

也就是说：

```text
按钮
=
Task Intent Resume Point
```

不是：

```text
按钮
=
执行脚本
```

这是非常关键的架构区别。
