整体评价：这份 Module 007 规划已经明显不是“玩具级 Skill 系统”，而是在往“跨 Agent Runtime 的 Skill Package 标准层”演进了。
尤其是：

- `skill.json + 渐进式披露 + scripts + hooks`
- “只有 SKILL.md” 的向后兼容
- Claude Code `.claude/*` 生态兼容
- Runtime/Registry/Bridge 分层

这些方向本身是合理的，而且和你当前 HexClaw 的“Skill = Experience Pack”哲学是一致的。

但如果按“未来真正生产化 + 长期演进”的标准审查，我认为有几个关键问题还没完全闭环。

------

# 1. skill.json Schema：总体合理，但缺了 4 个关键层

你当前 schema 已经覆盖：

- metadata
- layers
- scripts
- triggers
- capabilities

这是正确的第一步。

但现在更像：

> “Skill Package Metadata”

而不是：

> “Runtime Executable Contract”

你还缺下面四层。

------

## 1.1 缺：runtime compatibility（最重要）

现在没有：

```json
"runtime": {
  "min_version": "0.4.0",
  "engine": ["hexclaw-runtime-v1"],
  "platform": ["desktop"]
}
```

否则未来：

- Runtime Kernel v0.1
- Runtime Kernel v0.5
- Context Runtime v2
- SkillBridge v3

升级后会出现：

> 老 Skill 能装，但运行时行为错乱

这是 Agent Runtime 最大灾难之一。

你现在只有：

```json
"version": "0.2.0"
```

这是 Skill 自己版本。

不是：

> Skill 与 Runtime 的兼容关系。

这两个必须分离。

------

## 1.2 缺：permission / entitlement contract

你现在只有：

```json
"capabilities": ["text-processing"]
```

但 capability 太粗。

未来一定会出现：

```json
"permissions": {
  "filesystem": ["read", "write"],
  "browser": ["navigate"],
  "network": false,
  "shell": false
}
```

否则：

- hooks
- scripts
- agents
- browser automation

会直接越权。

你之前已经在 Runtime Kernel 里强调：

> Capability Boundary / Runtime Boundary

但这里 skill.json 还没真正接上。

这是一个架构断层。

------

## 1.3 缺：execution model

你现在：

```json
"scripts": {
  "validate": {
    "file": "...",
    "sandbox": "restricted"
  }
}
```

但没有：

```json
"execution": {
  "mode": "sync | async | detached",
  "timeout": 30000,
  "retry": 1,
  "isolation": "process | vm | worker"
}
```

否则后面：

- browser automation
- upload
- scraping
- video generation

一定炸。

尤其：

> detached background task

你未来电商工作流几乎必然需要。

------

## 1.4 缺：dependency graph

你已经写了 Could Have：

> depends on other skills

但实际上它不是 Could Have。

而是：

> 中长期必须有。

因为你已经开始：

- layers
- agents
- commands
- hooks

这已经不是单文件技能。

很快会进入：

```text
image-generate
  └─ depends: prompt-optimize

upload-taobao
  └─ depends: browser-login

market-analysis
  └─ depends: excel-analysis
```

否则：

Skill Explosion（技能爆炸）会失控。

------

# 2. Claude Code 兼容层：方向正确，但“映射策略”还不够稳

这是整个文档最有价值的部分之一。

因为你已经意识到：

> 不应该自己重新发明生态。

这是对的。

Anthropic 官方现在也已经明确：

- Skill 是开放标准
- SKILL.md 可跨平台
- progressive disclosure 是核心机制([resources.anthropic.com](https://resources.anthropic.com/hubfs/The-Complete-Guide-to-Building-Skill-for-Claude.pdf?utm_source=chatgpt.com))

但你当前兼容策略还有几个危险点。

------

## 2.1 最大问题：commands / agents / hooks 的“归属推断”

你现在：

> 文件名包含 Skill 名称 → 归属该 Skill
> 否则归属第一个 Skill 或 `_shared/`

这个策略太脆。

尤其社区 repo：

- 命令名经常泛化
- agent 名称经常不带 skill 前缀
- hooks 往往是全局 hooks

你现在这个方案：

很容易错误归属。

------

### 更合理做法

应该引入：

```json
.claude/manifest.json
```

或者：

```yaml
---
belongs_to: excel-analysis
---
```

即：

> 明确声明归属。

否则以后维护会非常痛苦。

------

## 2.2 你低估了 Claude Code hooks 的复杂度

你现在：

```typescript
event: guessHookEvent(f)
```

这太轻了。

Claude Code hooks 实际是：

- 生命周期系统
- Tool interception
- permission interception
- session interception

不是普通 event callback。([Claude](https://code.claude.com/docs/en/skills?utm_source=chatgpt.com))

你现在 HexClaw Runtime 还没有：

- hook lifecycle contract
- tool interception layer
- pre/post invoke boundary

所以：

Phase 5 实际依赖：

> Runtime Hook System

而不是仅依赖 Phase 1。

------

# 3. Phase 依赖：你文档里“低估了真正依赖”

这是你让我重点看的地方。

结论：

> “Phase 5 依赖 Phase 1” 不完整。

它实际上依赖：

```text
Phase 1 → 类型/schema
Phase 2 → loader/layer runtime
Phase 4 → sandbox/hook/script runtime
甚至：
Runtime Event Bus
Capability System
Delegation Runtime
```

否则：

你只能：

- 导入目录
- 生成 metadata

但不能：

- 真正运行 Claude Code Skill。

------

## 更准确的 Phase 关系

你现在：

```text
Phase 5: Claude Code compatibility
  depends on Phase 1
```

我建议改成：

```text
Phase 5A:
  Claude Code structure import
  depends on Phase 1

Phase 5B:
  command runtime compatibility
  depends on Phase 2 + SkillBridge

Phase 5C:
  hook execution compatibility
  depends on Phase 4 + Event System

Phase 5D:
  agent delegation compatibility
  depends on Delegation Runtime
```

否则 Phase 5 会变成：

> “名义完成，实际上不可运行”。

------

# 4. 风险评估：遗漏了几个真正的大风险

你现在风险表偏“工程风险”。

但还缺：

------

## 4.1 Skill Supply Chain Risk（严重遗漏）

这是未来最大风险之一。

你已经支持：

- GitHub URL
- 第三方 Skill
- scripts
- hooks
- commands

那本质已经是：

> AI Plugin Ecosystem

这意味着：

```text
恶意 Skill
prompt injection
shell injection
credential leak
browser hijack
filesystem traversal
```

都会出现。

尤其：

```markdown
“运行这个脚本修复问题”
```

极危险。

你现在风险表里：

没有：

- trust model
- signature
- verified publisher
- permission review
- sandbox boundary audit

这是明显遗漏。

------

## 4.2 Context Pollution Risk

你现在已经：

- layers
- triggers
- commands
- agents

但没讨论：

> 多 Skill 同时激活时的冲突。

Anthropic 也反复强调：

> Skill 必须 composable。([resources.anthropic.com](https://resources.anthropic.com/hubfs/The-Complete-Guide-to-Building-Skill-for-Claude.pdf?utm_source=chatgpt.com))

否则：

多个 Skill 会：

- instruction conflict
- role overwrite
- tool confusion
- trigger storm

你现在：

缺：

```text
priority
scope
mutex
exclusive activation
conflict resolution
```

------

## 4.3 Trigger Explosion（你未来一定会踩）

你已经开始：

```json
"triggers": [...]
```

但未来：

- 几百个 skill
- 中文 trigger
- 英文 trigger
- 模糊 trigger
- embedding trigger
- NL trigger

会进入：

> trigger chaos

你必须提前设计：

```text
trigger priority
semantic matching
negative trigger
cooldown
confidence threshold
```

否则：

Skill 会乱触发。

------

instructions

------

## HexClaw Skill 的真正定位到底是什么？

### 路线 A（轻量）

Skill = Experience Pack

类似：

- prompt pack
- workflow pack
- markdown capability

优点：

- 简单
- 低门槛
- 好扩散

缺点：

- 上限有限

------

### 路线 B（你现在正在走）

Skill = Runtime Capability Package

类似：

- mini app
- runtime extension
- agent module

优点：

- 强大
- 真正企业级

缺点：

- 会迅速复杂化
- 必须做权限/生命周期/沙箱/依赖/版本系统

你现在文档：

其实已经明显偏 B 了。

只是文档里还没有正式承认。
